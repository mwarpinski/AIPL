# Handoff: where AIPL stands and what to do next

Written 2026-10-21 for an agent (or the owner) picking the work up on another computer, and rewritten 2026-10-27, after the language decisions, the robustness fixes, the A/B harness, and the showcase. It is a snapshot; the code and git history win if they disagree. Read this, then docs/LAUNCH_CHECKLIST.md ("Where we stand", the list of what is left), ROADMAP.md, and the plan named under "Next".

## Who the owner is and how they like to work

- An economist and junior Python/SQL developer; explain architecture in plain terms, not jargon.
- AIPL is a language for AIs, written by AIs. Choose what is correct and least error-prone for an AI; human ergonomics do not matter. Strict types, explicit at the point of use (which allocator, which promise), even if verbose, but never restating what is already plain.
- They value disagreement backed by evidence. Every critical claim (a reviewer's notes, another model's audit) gets a tested verdict before it is acted on. Re-verify any other agent's "done".
- They will never pay for a security audit (so no hand-written crypto for real traffic).
- Log each of your own AIPL mistakes in docs/design/AGENT_FRICTION.md (what, what the toolchain said, the feature that would prevent it).
- A training corpus of AIPL code is planned for later: zero incorrect code, no counterexamples. Not started; wait for the language to settle.

## Repository and branches

- GitHub repo, three long-lived branches: `main` (release), `development` (integration), and `testing` (where a batch is verified before it reaches `development`: the owner's process since 2026-10-27). Work happens on `features/<name>`, merges `--no-ff` into `testing` or `development` after the full CI below has passed on that exact tree, `development` merges into `main` (when the owner asks, and only if it merges without conflicts), and nothing is pushed to `main` without the owner's word. Check where things are with `git ls-remote origin`, not from this file.
- The agent on the owner's Apple Silicon Mac mini works on `features/apple-silicon` (docs/APPLE_SILICON_HANDOFF.md; its report is docs/APPLE_SILICON_REPORT.md). Claude merges `development` into it so it stays current; the owner merges it. Do not rebase it.
- One checkout is the owner's (`development`, shared with other agents); do your work in a worktree of your own: `git worktree add ../AIPL-work -b features/<name> origin/development`.
- **Safety rules:** never `git stash`, `git checkout <branch>`, `git reset`, `git restore` or `git clean` in a checkout with uncommitted work (undo an edit by editing it back); commit only your own files, by explicit path; do merges in a temporary detached worktree (`git worktree add --detach /tmp/x origin/development`); never refresh the seed (`bootstrap/`) without the owner's approval; merge to `main` only when asked.
## Before every push: the full CI, locally

CI on GitHub runs: build, clippy with `-D warnings`, `cargo test --release`, the AIPL test suite, `fuzz.py` and `run_fuzz.py`, the optimizer's comparison (`opt_diff.py`), the harness self-test, and the documentation check. Run **every** step, doc-only changes included (docs are tests; a README edit once broke CI), on the exact tree you will push, in a worktree of its own (`git worktree add --detach /tmp/ci <commit>`), never in a checkout being edited. `sh tools/ci.sh /path/to/checkout` runs them all in about 18 minutes (the tests, 69 binaries and 470 tests, take 15 of them); `sh bootstrap/build.sh` is the second step, about 8 seconds, and fails fast if the compiler's imported std uses a feature the checked-in seed cannot read.

The tests run through `tools/ci_tests.py` (each test binary in turn, as `cargo test` runs them, with cargo's environment from `.cargo/config.toml`; `CI_PLAIN=1` runs plain `cargo test`), which records every test's start, end, and time in `target/ci_tests.jsonl`. `sh tools/ci-status.sh [/path/to/checkout] [--watch [SECONDS]] [--all]` shows the steps and their times, the tests running now and for how long, each binary's result, time, and peak memory, the slowest tests, the failures with the start of their output, and how long the rest should take from the last run's times. Memory is per test binary: a binary's tests share one process. Do not edit a worktree while a suite runs on it.

## Open problems

- **The `openat2` fallback (done 2026-10-27; was pinned 2026-10-26).** Every file a native executable opens goes through `openat2` (aipl_src/native/wasi.aipl `emit_openat2`), which Linux has had since 5.6 and Rosetta 2 and some container profiles lack. Now, on ENOSYS or EPERM, a program built without `--sandbox` retries with `openat` (257; nothing is lost, `/` is preopened, but it follows `..` and symlinks out where `aipl-run` refuses); a `--sandbox` program probes `openat2` at start (`emit_openat2_probe`) and, without it, says so and exits 1. Tested by `tools/without_openat2.py`, a seccomp filter that fails the call with ENOSYS (or `--eperm`) for a command and its children: `tests/test_openat_fallback.rs`, and CI runs `tests/test_native.rs` that way (it skips the cases that test confinement, and expects the sandbox refusal). The seed refreshed the same day (from 01bc216) has it: `sh bootstrap/build.sh` finishes under `without_openat2.py` (tests/test_bootstrap.rs checks it, and fails with the previous seed's `cannot read entry file`). Left: a run under Rosetta 2 itself, on the owner's Mac.

- **tests/test_serve.rs's intermittent failures: found and fixed (2026-10-25).** They failed about one run in five, locally and on GitHub. Two causes, both in the tests' `free_port` (tests/test_serve.rs and tests/test_net.rs):
  1. It took ports with `bind(0)`, from the range every outgoing connection also uses, so one of the thousands of connections these tests make could take a port before its server bound it ("Address already in use"). Ports now come from 10000 up to the ephemeral range (/proc/sys/net/ipv4/ip_local_port_range), never twice in a run.
  2. The empty answers: it found a port free by listening on it and closing at once. Tests run as threads of one process while other tests start server processes, and a started process holds a copy of every open socket until it runs its program; so a probe, though closed, could stay listening for a moment in a half-started child. A client connecting then was reset ("Connection reset by peer"), and its server, which bound the port a moment later, never saw it. Shown by tools/flake/inherit.py (no process starting: 0 such connects in 2.1 million; four threads starting processes: 471 in 20 seconds), and by the logged failure (the client connected on its first try, 0.5 ms after the server was started, long before a VM server can listen). `free_port` now asks by connecting (refused: free) and never listens.
  After the fix: tests/test_serve.rs 20 runs of 20 passed (before: about 1 in 6 failed); tests/test_net.rs 5 of 5. tools/flake/ keeps the stress scripts and inherit.py. Found on the way, fixed 2026-10-26: killing `aipl serve --fresh` by its process id left its aipl-run child serving; it now becomes that aipl-run (exec), which removes its temporary module once read (tests/test_serve.rs `ending_aipl_serve_ends_the_server`).
- **A `let` inside a contract: fixed 2026-10-26.** `(req (block (let m:i32 (% n 2)) (eq m 0)))` verified and ran in the VM, but neither code generator took a contract's lets as locals ("Unbound local variable 'm'"). Both now collect them after the body's, in the same order (src/compiler/wasm.rs, aipl_src/codegen.aipl); tests/test_language_gaps.rs `a_contract_may_bind_a_let`, every backend and both toolchains' bytes. Found by the optimizer's inliner.
- **Sugar inside a formatting placeholder: fixed 2026-10-26.** The Rust resolver refused `(println "n {(arr.len (arr.new i32 a 3))}")` (the self-hosted one compiled it): it now rewrites sugar a second time after splitting the format strings (resolver.rs read_module), with the same messages for a malformed form there; tests/test_sugar.rs. Still open: a trap in a placeholder's code is reported at the string literal, not at the access; giving placeholder code the columns it has inside the string would make such a trap's position exact.
- **Two small frictions, open** (docs/design/AGENT_FRICTION.md rows 68 and 69): `aipl verify` says OK for a file whose `(test ...)` bodies do not type-check (they are read only in a test build), and `aipl-run PROG -- ARGS` passes the `--` to the program, as `aipl run` and `aipl eval` do not.
- The Rust compiler stays for now as the independent second compiler that keeps the seed trustworthy (bootstrap/README.md); retiring it is a later decision.

## Things that are deliberately odd

- Line 404 of `aipl_src/native/x64.aipl` is an unreadable hex line (the "moves" test key). It must stay on line 404; do not wrap or comment it. If asked what it means: "explanation not found".
- The checked-in seed is `bootstrap/aipl-linux-x86_64`. Compiler-imported std files (vec, str, buf, alloc, os, map...) may only use features the seed knows; refresh the seed only with the owner's approval.
- `tools/fuzz.py` and `tools/run_fuzz.py` are program generators: when a language rule changes, they must follow it.
