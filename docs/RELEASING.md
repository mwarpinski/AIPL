# Releasing AIPL

How a release is made, and what each platform gets. The release is built by `.github/workflows/release.yml`; nobody
uploads anything by hand.

## What ships

| Platform | Status | In the tarball |
|---|---|---|
| Linux x86-64 | first-class | the self-hosted `aipl`, built from the checked-in seed with no Rust compiler (`sh bootstrap/build.sh`), and `aipl-net` |
| Linux AArch64 | first-class | the same, built on an AArch64 machine from the AArch64 seed |
| macOS (Apple Silicon) | preview | the Rust `aipl` and `aipl-run`; `aipl compile --exe` there bundles a 15 to 20 MB launcher |
| Windows x86-64 | preview | the same, as a zip installed by `install.ps1` |

macOS and Windows are a preview because they ship the Rust `aipl` until the Mach-O and PE backends exist; the
self-hosted `aipl` replaces it there when they do. First-class means built from the seed with no Rust compiler, and
installed and tried on a real machine of that kind before the release.

**`aipl-net` is the one Rust program in the Linux tarball.** It resolves host names and does TLS for native
executables, which are static machine code and can hold neither. It is built by its own workflow step
(`cargo build --release --locked --bin aipl-net`), and AIPL never writes TLS itself. Its replacement belongs to the
Rust removal track (docs/LAUNCH_CHECKLIST.md, section 5). Because it is a dynamic glibc program, the Linux legs are built
on Ubuntu 22.04: it needs glibc 2.35 or newer (the build checks it needs no more). The `aipl` in the tarball is a static executable and needs no libc, so
it also runs where there is no glibc (Alpine, a container with nothing in it); there, `aipl-net`, and so host names
and https, do not work.

## Cutting a release

1. Merge to `main` and let CI finish there. The release refuses a commit whose CI run did not pass.
2. Set the version: `python3 tools/release_check.py set X.Y.Z`. The version lives in `aipl_src/aipl.aipl` (what
   `aipl --version` prints, and the source of truth), `Cargo.toml` and the `aipl` package in `Cargo.lock`. CI runs
   `python3 tools/release_check.py version` and fails when they differ. Commit, and let CI pass again.
3. Rehearse if anything about the release machinery changed: Actions, "Release", "Run workflow". On a branch it builds,
   install-tests and signs every platform and publishes nothing. `sh tools/release_dry_run.sh` does the Linux leg on
   any Linux machine.
4. Tag and push: `git tag vX.Y.Z && git push origin vX.Y.Z`.

The workflow then:

1. **gate**: the tag names the version in all three places, the seeds are the ones `bootstrap/README.md` records
   (`python3 tools/release_check.py seeds`), the tagged commit is on `main`, and its CI run passed.
2. **build**, on four machines: Linux x86-64 and AArch64 build the self-hosted `aipl` from the seed and check that it
   says `aipl X.Y.Z`; macOS and Windows build the Rust `aipl`. Each packs its tarball (a zip on Windows) and installs it
   into an empty home with `install.sh` (`install.ps1`), as a user would, and runs it.
3. **sign**: one `SHA256SUMS` lists every file; Sigstore signs it keyless (`SHA256SUMS.bundle`), and the workflow
   verifies the signature the way a user would before it goes on.
4. **publish**: a GitHub release with the tarballs, their `.sha256` files, `SHA256SUMS` and its bundle, and notes
   generated by `tools/release_notes.py` (platform status, install and verify commands, the commits since the last tag).

## Verifying a download

```sh
BASE=https://github.com/mwarpinski/AIPL/releases/download/vX.Y.Z
curl -sSLO $BASE/SHA256SUMS && curl -sSLO $BASE/SHA256SUMS.bundle
cosign verify-blob --bundle SHA256SUMS.bundle \
  --certificate-identity 'https://github.com/mwarpinski/AIPL/.github/workflows/release.yml@refs/tags/vX.Y.Z' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com SHA256SUMS
sha256sum -c SHA256SUMS --ignore-missing
```

There is no key to trust or to lose: the certificate says the file was signed by this repository's release workflow for
this tag, and the signature is in Sigstore's public log. `install.sh` checks the tarball against its own `.sha256` and
does not verify the signature itself. macOS and Windows binaries are not notarised or code-signed yet (see
docs/LAUNCH_CHECKLIST.md, section 4), which is part of why they are a preview.

## The seeds

`bootstrap/aipl-linux-x86_64` and `bootstrap/aipl-linux-aarch64` stay in git; a clone builds the compiler with no
network. Each seed's SHA-256 is recorded in `bootstrap/README.md`, and CI fails when a seed changes without it. A seed
is refreshed only when the compiler's own source needs a form the old one does not know. The release does not need a
refresh for that reason alone: the shipped `aipl` is stage 2, built from the tagged source.
