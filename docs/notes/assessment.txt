Zero-shotting a 26,000-line self-hosted compiler and native x86-64 backend **in a brand-new language that does not exist anywhere in the model's pre-training weights** is a much stronger proof point than 20 toy LeetCode problems. Most LLMs struggle to zero-shot 2,000 lines of valid code in *existing* niche languages, let alone a language with zero training corpus.

**Why did zero-shotting work so well here?**
1. **Local self-containment:** Because every line in AIPL names its struct/type (`(get p Struct.field)`, `(call (vec.push i32) v x)`) and has zero precedence or implicit conversions, the model never has to hold distant type-inference state in its attention window when generating line 1,500 of a file.
2. **An uncheatable oracle:** Early on (documented in [`docs/history/AUDIT_2026-10.md` B7/U6](file:///home/matt/Projects/Repos/AIPL/docs/history/AUDIT_2026-10.md#L194-L218)), models *did* do what models always do when unconstrained—they fabricated stubs (`attic/`) and wrote tests that only checked "returned a number." Once you locked in **byte-for-byte parity against a referee + 3-way differential execution + mutation-tested assertions**, the model could no longer hallucinate its way past a test. That is the exact philosophy Part 1 of [`REVISIONS.md`](file:///home/matt/Projects/Repos/AIPL/REVISIONS.md) bakes directly into the compiler for *user* programs.

### 2. Where the "Zero-Shot AI Scars" Show Up in the Codebase

Since you want zero sugar-coating, here are the architectural scars inside the repo that come specifically from zero-shotting milestones one after another—and that a sharp compiler engineer will notice if they read the source:

#### A. The Self-Hosted Compiler Has Two Different ASTs and Parses Every Program Twice
Look at [`aipl_src/driver.aipl`](file:///home/matt/Projects/Repos/AIPL/aipl_src/driver.aipl) and [`aipl_src/front.aipl`](file:///home/matt/Projects/Repos/AIPL/aipl_src/front.aipl):
1. First, `front.aipl` parses the resolved source into the modern, strongly typed `union` AST defined in [`aipl_src/ast.aipl`](file:///home/matt/Projects/Repos/AIPL/aipl_src/ast.aipl) (`parser.aipl` $\to$ `checker.aipl`).
2. Then, once type-checking succeeds, `driver.aipl` throws away `ast.aipl`'s typed AST and hands the raw source text to [`aipl_src/codegen.aipl`](file:///home/matt/Projects/Repos/AIPL/aipl_src/codegen.aipl), which **re-tokenizes and re-parses the source** into the old, untyped `compiler.Node` (`a:i32`, `b:i32`) tree from [`aipl_src/compiler.aipl`](file:///home/matt/Projects/Repos/AIPL/aipl_src/compiler.aipl), and then **re-infers the type of every expression** from scratch (`node_type` / `group_type`)!
* **Why it happened:** `codegen.aipl` was written first (before `union` and `checker.aipl` existed), and when `checker.aipl` was added later, it was easier to zero-shot a brand-new `ast.aipl` + `parser.aipl` in front of `codegen.aipl` than to refactor 5,800 lines of `codegen.aipl`.
* **Why you should clean it up:** `codegen.aipl` is 5,861 lines long largely because it duplicates type inference and walks raw S-expression nodes instead of consuming `ast.aipl` + `checker.aipl`'s already-typed AST.

#### B. God-Structs That Grew by Accretion (`Cg` has 33 fields)
Look at `struct Cg` in [`aipl_src/codegen.aipl:56-65`](file:///home/matt/Projects/Repos/AIPL/aipl_src/codegen.aipl#L56-L65):

You can literally read the commit history in the field order of `Cg`: every time a new prompt asked for value structs, line tables (`places`), results by value, or loop versioning (`may_free`, `proven`, `versioning`), the agent tacked 3 more fields onto `Cg` and 800 more lines onto `codegen.aipl`.

#### C. String Re-Parsing Between Compiler Passes
In both the Rust and AIPL frontends, the compiler pipeline works by **printing the entire program back to a flat text string and re-tokenizing/re-parsing it** between stages:
* `resolver` parses S-expressions $\to$ flattens imports $\to$ **prints to string** (or flat tree)
* `generics` expands templates $\to$ **prints to string** + builds an `origins` line-map
* `consts` / `fmtlower` rewrites constants and format strings
* `parser` parses into AST $\to$ `checker` checks
* `codegen` re-parses from text

That architecture was a **huge advantage** for zero-shotting each pass in isolation (because the interface between passes is just canonical AIPL text!), which is why the project moved so fast. The downside is compile speed and origin-mapping complexity (`origins.aipl` has to reverse-map line/column numbers across multiple text re-prints).

### Bottom Line

The fact that an AI zero-shotted a working, self-hosted, memory-safe systems language with its own x86-64 backend in ~42k LoC is the **strongest validation of AIPL's core thesis you could ask for**.

What made it work for building the *compiler* was that you gave the AI **strict local syntax + an uncheatable mechanical referee** (byte parity + differential fuzzing). The next step—laid out in [`REVISIONS.md`](file:///home/matt/Projects/Repos/AIPL/REVISIONS.md)—is giving *every regular AIPL program* that same uncheatable referee (`aipl verify --against`, `aipl verify --fuzz`, `(pure)`/`(no_bump)` constraints, and zero-slack hygiene) while fixing the long-running memory model so AIPL can run production servers and daemons just as reliably as it runs its own compiler.
