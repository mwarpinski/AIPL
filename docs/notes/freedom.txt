That feeling you have—*"I have this crazy compiler, but I feel like I can't leave the git repo or do anything without `cargo` holding my hand"*—is **the exact definition of "inverted maturity."**

### What "Inverted Maturity" Means Here

Most new languages build the **outside** first and fake the **inside**:
- **Normal new language (Year 1):** Has a slick `curl | sh` installer, `my_lang init`, `my_lang build`, `my_lang run` that work from any directory on your laptop—and under the hood it's just transpiling to C or Python because the compiler is a toy.
- **AIPL today:** You built the **Year-5 compiler internals** first. You have a self-hosted compiler ([`aipl_src/aipl.aipl`](file:///home/matt/Projects/Repos/AIPL/aipl_src/aipl.aipl)) that compiles AIPL $\to$ WebAssembly $\to$ standalone native Linux x86-64 ELF machine code with **zero Rust, zero LLVM, and zero libc**.
- **Why you feel stuck inside Cargo:** The "front door" (the last 100 lines of CLI glue and path lookup) still assumes your current working directory is `/home/matt/Projects/Repos/AIPL`!

Look at the 4 tiny paper cuts that currently trap you inside the repo:

1. **The Standard Library Path is Hardcoded to the Repo:**
   - In the self-hosted CLI ([`aipl_src/aipl.aipl:70-71`](file:///home/matt/Projects/Repos/AIPL/aipl_src/aipl.aipl#L70-L71)) and [`codegen_opt.aipl:2357-2358`](file:///home/matt/Projects/Repos/AIPL/aipl_src/codegen_opt.aipl#L2357-L2358):
     ```lisp
     (let std_dir:(ptr str.Bytes) (call os.env "AIPL_STD"))
     (if (lt (get std_dir str.Bytes.len) 0) (set! std_dir (call str.from_str "aipl_src/std/")) (block))
     ```
     If you `cd ~/Desktop` and run the self-hosted `aipl` binary without setting `AIPL_STD`, it looks for `~/Desktop/aipl_src/std/` and immediately fails on `(import io)`!
   - And in the Rust CLI ([`src/resolver.rs:880`](file:///home/matt/Projects/Repos/AIPL/src/resolver.rs#L880)), it hardcodes `env!("CARGO_MANIFEST_DIR")/aipl_src/std` at compile time—which only works if `/home/matt/Projects/Repos/AIPL` stays right where it is on your disk.

2. **The Self-Hosted [`aipl_src/aipl.aipl`](file:///home/matt/Projects/Repos/AIPL/aipl_src/aipl.aipl) Only Exposes `compile` and `--version`:**
   - Look at [`aipl_src/aipl.aipl:24-27`](file:///home/matt/Projects/Repos/AIPL/aipl_src/aipl.aipl#L24-L27): the standalone self-hosted binary already contains the full type-checker ([`front.aipl`](file:///home/matt/Projects/Repos/AIPL/aipl_src/front.aipl)) and native x86-64 backend ([`native.aipl`](file:///home/matt/Projects/Repos/AIPL/aipl_src/native/native.aipl)), **but its `main` function only checks for `aipl compile`!**
   - It doesn't expose `aipl verify`, `aipl test`, or `aipl build`, so you keep falling back to `cargo run -- verify` or `./target/debug/aipl test`.

3. **WASI `fs.open` Doesn't Set the Executable Bit (`chmod +x`):**
   - When the self-hosted compiler writes a native ELF binary via `aipl compile --exe app.aipl -o app`, WASI's `path_open` creates the file with permissions `0644` (not `0755`). You have to manually run `chmod +x ./app` before you can execute it (noted in [`aipl_src/aipl.aipl:14-15`](file:///home/matt/Projects/Repos/AIPL/aipl_src/aipl.aipl#L14-L15)).

4. **Requiring `-o OUT` Every Time:**
   - You have to type `aipl compile --exe hello.aipl -o hello` instead of `aipl build hello.aipl` (defaulting the output binary name to `./hello`).
